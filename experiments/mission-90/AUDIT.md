### 1.1 Baseline caveats (measured, not assumed)

- **Coverage run interference.** A coverage run executed concurrently with
  a second full-suite run produced 188 `FileNotFoundError` errors and a

## 3. Findings: core primitive (`src/world/`)

### C-1. High, VERIFIED: server `GET /v1/state` bypasses checkpoint pin verification (F3a)

`src/world/server.py:140-166`. `get_state` resolves a checkpoint name to
a seq itself via `work.checkpoints()` and calls `work.state(version=seq)`,
never `work.state(checkpoint=...)`. The F3a pin check
(`core.py:578-608`) is skipped on the HTTP read path. Live probe: after
repointing checkpoint `c1` from seq 1 to seq 2 by direct DB edit, core
`state(checkpoint="c1")` raised `InvariantViolation`, but
`GET /v1/state?checkpoint=c1` returned 200 with the seq-2 document.
This defeats the exact attack F3a was added to stop and contradicts
README.md ("the pin is verified on read and resume"). No test covers a
repointed checkpoint over HTTP.
Fix: call `work.state(checkpoint=checkpoint)` and map
`InvariantViolation` to 422 (or 409).

### C-2. High, VERIFIED: `redact_field` misses encrypted fields in REJECTED rows after the latest committed version

`src/world/core.py:1315-1330`. `redact_field` iterates
`range(1, self.version + 1)`; `version` is the latest COMMITTED seq. A
REJECTED row appended after the latest committed version is never
visited, and `_envelope_at` (`core.py:1257`) would skip it anyway
because it uses committed-only `state(version=seq)`. Live probe:
committed seq 1 plus rejected seq 2, both with encrypted `ssn`;
`redact_field` returned receipts for seq 1 only and the rejected row's
envelope was still decryptable afterwards. The receipt then falsely
implies the field is shredded everywhere.
Fix: iterate over `MAX(seq)` from `versions` and resolve envelopes via
`proposal(seq)`; add a test with a trailing REJECTED row.

### C-3. Medium, VERIFIED: unvalidated request bodies on POST routes return 500 instead of 400

`src/world/server.py:178, 210, 225`. `post_update`, `post_checkpoint`,
and `post_resume` call `await request.json()` with no error handling
and pass body fields straight through. Probes on `/v1/update`: malformed
JSON returns 500, JSON array body returns 500, `"note": 123` returns 500
(`_row_hash` joins a non-string), `"expected_version": "x"` returns a
misleading 409 instead of 400. No test posts malformed JSON to `/v1/*`.
Fix: wrap `request.json()` in try/except returning 400; validate the
body is a dict and that `state` is a dict, `actor`/`note`/
`idempotency_key` are strings or null, and `expected_version` is an int
or null, before calling core.

### C-4. Medium, VERIFIED: `GET /v1/state` on an empty world returns 404 instead of the empty document

`src/world/server.py:155-166`. With no `version`/`checkpoint` given,
`get_state` sets `seq = work.version` (0 on an empty world) and calls
`work.state(version=0)`, which raises `KeyError`. Core `state()` with no
version returns `{}` for an empty world, and `GET /health` already
reports `version: 0`, so the HTTP API contradicts the core API.
Fix: when `work.version == 0` and no version/checkpoint was requested,
return `{"version": 0, "state": {}}` directly.

### C-5. Medium, VERIFIED: invariant judgment runs outside the write lock; README overstates atomicity

`src/world/core.py:327-354` vs README.md. `update()` reads `old`, judges
invariants, and only then executes `BEGIN IMMEDIATE`. With
`expected_version` the in-transaction re-check catches staleness via
`ConflictError`, but without it the write is last-writer-wins on a
snapshot that may already be stale, so invariants were judged against
history that is not what gets committed. README says judgment and append
are atomic; only the version re-check plus append is. `update_many`
does judge inside the transaction, so the two paths differ.
Fix: correct the README wording to say the version check and append are
atomic and that judgment freshness requires `expected_version`. Moving
judgment inside the lock would change the deterministic-simulator
assumption noted in the code comment, so that needs an ADR, not a quiet
change.

### C-6. Medium, VERIFIED: `world import` silently orphans encrypted fields

`src/world/cli.py:215-239`. `cmd_import` replays each COMMITTED row with
`w.update(row["state"], ...)` but never imports `field_keys`. An
exported world containing encrypted fields imports cleanly while every
envelope in it is permanently undecryptable (`RedactedError: "never
escrowed"`). The docstring warns only about rejected rows and the fresh
hash chain.
Fix: export/import `field_keys` rows alongside the JSONL (documenting
that the master key must be carried separately), or refuse/warn when an
imported row contains an envelope with no escrowed key.

### C-7. Medium, VERIFIED: transcript import has a lost-update race

`src/world/producers/transcript.py:37-52`. `import_transcript` does
`state = work.state()` then `work.update(state, ...)` with an
idempotency key derived only from the transcript text. The key dedupes
re-imports of the same text, but two different transcripts imported
concurrently both read the same base document and the second overwrites
the first's merged items. This is the exact lost-update pattern
`expected_version` exists to prevent.
Fix: use `work.read()` to get `(state, version)` and pass
`expected_version=version`, retrying on `ConflictError`; add a
two-thread concurrent-import test.

### C-8. Medium, VERIFIED: `encrypt_fields` silently skips fields nested in lists

`src/world/core.py:1071-1115`. `encrypt_fields` resolves each field
with `_get_path`, which only descends through dicts; a present field
such as `items.0.secret` resolves to missing and is skipped like an
absent field. Probe: `encrypt_fields` on `{"items": [{"secret": "x"}]}`
returned 0 records with the plaintext untouched. Compounding it,
`decrypt_fields` builds list paths as `a[0].secret` (`core.py:1252`)
while encryption AAD would use the caller's `a.0.secret` form, so even
a hand-built list-nested envelope would fail authentication on decrypt.
Fix: teach `_get_path` (and the swap loop) to handle numeric list
indices, or raise `ValueError` for fields that traverse a list instead
of silently skipping; align the AAD path format between encrypt and
decrypt; add a test.

### C-9. Medium, VERIFIED: CLI `diff`/`blame`/`import` leak tracebacks on ordinary errors

`src/world/cli.py:185-239`. `cmd_diff` and `cmd_blame` do not catch the
`KeyError` that `World.state`/`blame` raise for unknown/rejected
versions, and `cmd_import` does not catch `InvariantViolation`/
`ConflictError` from `w.update`. `main()` catches only
`ValueError`/`TypeError`, and `InvariantViolation` inherits directly
from `Exception`. Probe: `world diff probe --from 99` printed a full
traceback. `cmd_state`/`cmd_update`/`cmd_resume` handle these errors
cleanly, so this is an inconsistency, not a design choice.
Fix: catch `KeyError` in `cmd_diff`/`cmd_blame` (print `error: ...`,
exit 1, as `cmd_state` does) and `InvariantViolation`/`ConflictError`
in `cmd_import` (abort with a clear message noting earlier rows were
already committed).

### C-10. Low, VERIFIED: `POST /v1/resume` drops `expected_version` / `idempotency_key`

`src/world/server.py:221-240`. `post_resume` passes only `name`,
`actor`, and `note` to `work.resume`, although core `resume()`
(`core.py:660`) accepts `expected_version` and `idempotency_key`.
README says `world serve` "exposes the same model over HTTP"; over
HTTP, resume cannot do optimistic concurrency or idempotent retry.
Fix: forward both fields from the body (with the C-3 validation) and
return 409 on `ConflictError`, matching `post_update`.

### C-11. Low, VERIFIED: `world update-many` has no way to pass idempotency keys

`src/world/cli.py:62-77, 364-372`. Core `update_many` (`core.py:383`)
accepts a parallel `idempotency_keys` sequence, but the CLI defines no
`--idempotency-keys` flag and never passes one. The batch path is
therefore unusable for idempotent replays from the CLI, while single
`world update` supports `--idempotency-key`.
Fix: add an optional `--idempotency-keys` flag and validate its length
matches the states.

### C-12. Low, NEEDS VALIDATION: no busy-timeout / retry on SQLite lock contention

`src/world/core.py:206`. `_connect` uses `sqlite3.connect(self._path)`
with the default 5 s timeout and no `busy_timeout` pragma. Under write
contention, `BEGIN IMMEDIATE` can raise `sqlite3.OperationalError:
database is locked`, which `update()`/`update_many()` do not catch; it
surfaces as a CLI traceback or a server 500 rather than a retry or a
409/429. Light-load concurrency tests pass, so this needs a contention
test to confirm at what writer count it bites.
Fix/verify: set a `busy_timeout` pragma in `_connect`, or add a bounded
retry around `BEGIN IMMEDIATE`; add a many-writer contention test
asserting no `OperationalError` escapes.

### C-13. Low, VERIFIED: `update_encrypted` spans three transactions

`src/world/core.py:1159-1188`. `update_encrypted` escrows keys (its own
commit), then `update` (its own commit), then tags the keys with the new
seq (a third commit). A crash or `ConflictError` between steps 1 and 3
leaves key rows with `seq = NULL`. Decryption still works, so this is
audit-linkage loss, not data loss, and the docstring's "escrowed before
the update" rationale covers the rejected-proposal case, but the crash
window is not documented.
Fix: document the window in the docstring, or fold the seq-tagging into
the same transaction as the update where possible; add a test asserting
keys stay decryptable when the update raises `ConflictError`.

### C-14. Low, VERIFIED: transcript producer crashes with a traceback if `world_engine` is not installed

`src/world/producers/transcript.py:25`, `src/world/cli.py:241-249`.
`import_transcript` does a bare `from world_engine.ingestion.transcript
import parse_transcript` with no `ImportError` handling, and
`cmd_import_transcript`/`main()` do not catch `ImportError` either. On
an install without the `world_engine` package, `world import-transcript`
dies with a traceback instead of the clean "needs the X extra" message
that `cmd_serve` provides for missing `uvicorn`.
Fix: catch `ImportError` in `cmd_import_transcript` and print a clean
error naming the missing dependency, mirroring `cmd_serve`.

### C-15. Low, VERIFIED: `decrypt_fields` error can lose the field path on nested envelopes

`src/world/core.py:1217-1255`. The `walk` helper re-raises
`RedactedError` with the computed path `p`, but for envelopes nested
inside lists the path is built as `a[0].secret` while `_envelope_at` /
`redact` identify fields by the dot form `a.0.secret`, so the `field`
in the error does not match the identifier the user would pass to
`redact_field`. Entangled with C-8.
Fix: settle on one path notation for list indices and use it in
`encrypt_fields`, `decrypt_fields`, and `redact_field`.

### Core areas checked and clean

- Hash chain / `verify()` (`core.py:790-820`): recomputes every link,
  streams rows; seq gaps alone cannot forge a link. Tail rollback is
  undetectable without signed tips, which is documented, not a bug.
- Merkle root / inclusion proofs (`core.py:1390-1428`): sibling
  left/right handling and odd-level duplication are consistent between
  `inclusion_proof` and `verify_inclusion`.
- Ed25519 (`ed25519.py`): RFC 8032 vectors tested; `checkvalid`
  rejects bad lengths, `s >= L`, and off-curve points without raising;
  non-constant-time operation is documented in the module docstring.
- Field crypto (`fieldcrypto.py`): encrypt-then-MAC, tag verified
  before decryption with `hmac.compare_digest`, AAD binds
  world/field/key_id; nonce is fresh random per encryption.
- Handoff validation (`handoff.py:246-330`): duplicate ids, dangling
  `supersedes`/`evidence_ids`/`validated_by`, superseded-without-exactly-
  one-successor, and supersession cycles are all checked.
- Server auth (`server.py:110-137`): fails closed with no key,
  `hmac.compare_digest` for the key, `X-Forwarded-For` honored only
  with `trust_forwarded_for`, rate limit applies after auth.
- Invariants (`invariants.py`): `monotonic`/`type_stable` first-write
  semantics, `respect_locks` ignoring non-list lock keys, and `all_of`
  collecting all reasons match their docstrings.

## 4. Findings: legacy engine, SDK, surfaces, deploy

### L-1. High, VERIFIED: `render.yaml` as written cannot start

`render.yaml:6` builds with `pip install -e .` (no extras) while
`render.yaml:7` starts `uvicorn app:app`; `pyproject.toml:28` has
`dependencies = []` and fastapi/uvicorn live only in the `[server]`
extra. Reproduced in a clean venv with the exact build command:
`import app` fails `ModuleNotFoundError: No module named 'fastapi'`.
The repo's only deploy config would crash-loop on first deploy.
Fix: change `buildCommand` to `pip install -e ".[server]"` and verify
with a clean-venv smoke test in CI. Note: mission rule 5 forbids
deployment/hosting changes without approval; this fix needs Rosario's
say-so, it is not a Day 1 change.

### L-2. High, VERIFIED: legacy writes are unauthenticated unless the operator remembers to set the key

`src/world_engine/api/auth.py:40-41`. `require_api_key` silently
returns when `WORLD_API_KEY` is unset; the only signal is a startup log
warning (`src/world_engine/api/main.py:46-52`). `render.yaml:27-28`
declares `WORLD_API_KEY` with `sync: false` and no value, so a deploy
with the secret left unset serves open writes (plus `/rogue-attack`,
which appends 3 ledger rows per call). Already known as Prompt 3 open
finding F-open 1; repeated here because the legacy service is the one
`render.yaml` actually deploys.
Fix: fail startup (or refuse `0.0.0.0` binding) when the key is unset,
or set the key as a required Render secret with a deploy-time check.

### L-3. Medium, VERIFIED: "frozen prototype" contradicts the live deployment wiring

`docs/architecture.md:6` calls `world_engine` "a separate frozen
prototype", yet it is the only runnable service in the repo:
`render.yaml:7` deploys `uvicorn app:app` (legacy, via `app.py:9`), and
`pyproject.toml:65-66` still ships `world-server` / `world-import`
console scripts pointing at it. Nothing deploys the primitive's
`world serve`.
Fix: pick one, and record it in an ADR; do not leave a "frozen"
package as the sole deploy target.

### L-4. Medium, VERIFIED: shipped dashboard uses the deprecated `/api/*` routes slated for removal in v0.3.0

`static/dashboard.html:96,130,149` fetches `/api/state`, `/api/intent`,
`/api/rogue-attack`; `src/world_engine/api/main.py:16,21-24` promise the
`/api` aliases "will be removed in v0.3.0". Removing them breaks the
dashboard that ships in the repo.
Fix: migrate the dashboard to `/api/v1/*` now (the React landing page
already uses v1, `frontend/src/components/StatePanel.jsx:13`), then the
removal is safe.

### L-5. Medium, VERIFIED: SDK time-travel replay silently drops node locks; server replay honors them

`src/world_sdk/ledger.py:559-607` (`replay_to`) handles only
`REGISTER_ENTITY` and COMMITTED intent rows; `grep LOCK
src/world_sdk/ledger.py` returns 0 matches. The engine's
`replay_ledger` handles `LOCK_ENTITY`/`UNLOCK_ENTITY`
(`src/world_engine/core/engine.py:779-784`). So
`WorldClient.state_at_block()` reports a locked node as `ACTIVE`,
diverging from the server's replay of the same chain. The same function
also skips intents for entities absent from its state map, while the
engine materializes ledger-external entities from the row pre-image.
Fix: port the lock-flip and pre-image branches into `replay_to`, with
a test replaying a lock/unlock sequence through both implementations
and comparing.

### L-6. Medium, DOCUMENTED: idempotency keys are global, not scoped to entity or payload

`src/world_engine/core/engine.py:337-338`: "The key, not the payload,
defines identity, so a retried submission gets the first submission's
outcome even if the agent changed the fields." Two different agents (or
entities) reusing a key such as `retry-1` get the first verdict back,
silently. Same semantics duplicated in `src/world_sdk/ledger.py:216+`.
This is the open F3b decision already on the roadmap; fix is either to
scope keys per entity or bind the key into the row hash, per that
decision, not a silent behavior change.

### L-7. Medium, VERIFIED: unauthenticated GETs are unrated and two are unbounded/O(n)

`src/world_engine/api/middleware.py:71-91`. `_WRITE_LIMITS` covers only
POST `/intent`, `/entities`, `/rogue-attack`. `GET /api/v1/replay`
(`src/world_engine/api/v1.py:147`) runs a full-chain `verify_chain()`
plus replay on every request with no auth and no rate limit, and
`GET /api/v1/state` (`v1.py:48-53`) returns every entity with no
pagination. On a large ledger this is a trivially repeatable expensive
read.
Fix: rate-limit the GETs (or at least `/replay`), and cap/paginate
`/state`.

### L-8. Medium, VERIFIED: SDK duplicates the engine's intent path (~120 lines) and has already drifted by one branch

`src/world_sdk/ledger.py:216-360` (`LocalLedger.intent`) re-implements
`execute_deterministic_transition` instead of sharing it. Drift already
exists: the engine repairs an orphan idempotency-key mapping
(`engine.py:354-355`); the SDK has no equivalent branch.
Fix: extract the shared transition into one function both call, or add
a parity test covering the orphan-key path in both.

### L-9. Low, VERIFIED: `world_engine/__init__.py` documents a root shim that does not exist

`src/world_engine/__init__.py:8-9` says shims remain at the root as
"`engine.py`, `ingest.py`, `app.py`" with "`python ingest.py`" as a
working entry point. Repo root contains only `app.py`, `engine.py`,
`import_transcript.py`; there is no `ingest.py`.
Fix: correct the docstring to `import_transcript.py` / `world-import`.

### L-10. Low, DOCUMENTED: `pyproject.toml` still describes `world_engine` as "the kernel"

`pyproject.toml:39-44` comment: "the kernel lives in
`src/world_engine/`". The primitive in `src/world/` is the kernel now;
already flagged in the Prompt 6 audit
(`experiments/prompt6/AUDIT.md:583-589`).
Fix: rewrite the comment to name `src/world/` as the kernel and
`src/world_engine/` as the legacy demo.

### L-11. Low, DOCUMENTED: rate limiting trusts the first `X-Forwarded-For` entry

`src/world_engine/api/middleware.py:94-101` (`_client_ip`) uses the
first XFF value as the client IP. A hostile client can rotate IPs and
dodge the per-IP bucket. The code comment states the tradeoff
explicitly (alternative is rate-limiting the whole Render proxy as one
client).
Fix: only trust XFF when the direct peer is a known proxy, or accept as
documented demo behavior.

### L-12. Low, VERIFIED: `tools/export_ledger.py` mutates state

`tools/export_ledger.py:22` calls `init_db()` before reading;
`init_db()` creates the tables and seeds the default entity when empty.
Running the export against a fresh checkout creates `world_state.db`
as a side effect.
Fix: open the DB read-only
(`sqlite3.connect(f"file:{path}?mode=ro", uri=True)`) and fail clearly
if it does not exist.

### L-13. Low, DOCUMENTED: demo signing key lives in source

`demo/common.py:22`: `DEMO_TIP_KEY = "demo-tip-key-not-a-secret"`, with
a comment stating it is demo-only. Harmless as documented, but any
copy-paste of the demo into real code carries a known key.
Fix: read it from `WORLD_DEMO_TIP_KEY` env with the constant only as a
fallback, or leave as is and note it in `demo/README.md`.

### L-14. Low, VERIFIED: the two shipped UIs call different API versions

`static/dashboard.html` uses deprecated `/api/*` (L-4) while the React
landing page uses `/api/v1/*`. The frontend build in `static/site/` is
current with `frontend/src/` (both last touched by `e66ee58`,
2026-09-22), so this is a consistency nit, not staleness.
Fix: same as L-4, migrate the dashboard to v1.

### Legacy areas checked and clean

- No SQL injection anywhere in the legacy layer (all queries
  parameterized).
- Write routes are per-IP rate-limited (120/60/5 per min).
- NaN/Infinity rejected before constraint checks; check-then-act under
  `BEGIN IMMEDIATE`.
- `docs/SECURITY.md` Part B accurately scopes the legacy threat model.
- The README's "not the product direction" claim is correctly stated

## 5. Findings: tests, spec, CI

### T-1. High, VERIFIED: `test_soak_no_latency_drift` is flaky under load

`tests/test_soak.py:36-38`. Under concurrent load (two full suites at
once) it failed with `p99 drift: [0.0016, 0.050, 0.0466, 0.0501]`
(first chunk 1.6 ms, later chunks about 50 ms, 30x ratio vs the 5x
limit; the last chunk also marginally exceeds the 0.050 s absolute
cap). Re-running the file alone passed in 2.41 s, and it passes in
every clean sequential run. The assertions are wall-clock timing on a
shared-CPU VM, so the baseline goes red whenever the host is loaded.
Fix: replace the absolute 50 ms cap and 5x ratio with a load-insensitive
check (e.g. assert per-update cost grows sub-linearly via row-count
scaling, or move the timing gate to a benchmark job with retries), or
mark the timing assertions as non-gating and keep only the `verify()` +
version assertions as the CI gate. First fix of the mission: do not
build on a tree whose baseline can go red from host load.

### T-2. High, VERIFIED: CI installs unpinned `ruff` and `mypy`

`.github/workflows/ci.yml:40` (`pip install ruff mypy`). A new
ruff/mypy release can break or silently change the lint job; already
