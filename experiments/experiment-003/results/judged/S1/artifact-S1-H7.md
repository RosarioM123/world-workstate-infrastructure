This work is about adding rate limiting to a gateway service that fronts a multi-instance API, with six instances sitting behind a load balancer. That shape matters from the start, because a limit counted separately on each instance would not amount to a single limit for a client at all, so whatever is built has to give a consistent view of a client's usage across all six instances. Redis helps here, since the team already operates Redis in all environments and it is already a dependency of the service, which also keeps the work inside one of the standing constraints, that no new external dependencies should be added beyond what the service already uses. The other standing constraints are just as firm. Rate limiting may add at most 5 ms at p99, and counters must survive deploys, so a deploy must not reset a client's usage.

Some of this is already built and merged, and some of it is only decided, and the distinction matters for whoever picks this up next. A rate limit middleware skeleton has been written and merged behind a feature flag, so the rollout guard is in place even though the final design is not yet fully landed. Early on there was a bug in how counters were stored, because counters kept in process memory reset on every deploy and differed from instance to instance, which conflicted directly with the consistency and deploy survival requirements above. That bug was fixed and the fix is merged. Counters moved to Redis with a shared key per client, which gives one counter view per client across instances and avoids counters resetting on deploy, and the fix is covered by a regression test, although the name of that regression test is not given in the materials left from the session.

The design as it stood at the start of the session did not survive the session unchanged. The initial algorithm was a fixed window counter, chosen simply because it was the simplest approach to implement, and the default limit at that point was 100 requests per minute per client, taken from the original API spec. Both of those decisions were later superseded, and in both cases the change came from new evidence arriving partway through the session rather than from a change of preference.

For the algorithm, a load test of the fixed window implementation showed a boundary burst problem. Around a window edge a client could send twice the limit, by sending 100 requests at the end of one window and another 100 requests at the start of the next. The load test report recommended a token bucket algorithm instead, and it noted that a prototype branch already implements token bucket and passed the same load test without boundary bursts. Token bucket is therefore the current accepted design and it replaces the fixed window choice, but it should not be treated as merged. The code exists on the prototype branch, and the materials do not say that branch has been merged, so merging it is still outstanding work. Shipping the fixed window version instead would mean knowingly keeping the 2x burst at window edges that the load test found.

The default limit changed for a different reason. Support reported that a legitimate batch client was being throttled at 100 requests per minute, and in a product review meeting the product decision was made that the default becomes 600 requests per minute per client, effective with this release. That decision supersedes the earlier 100 requests per minute default. As with the algorithm change, the decision is made and is meant to apply with this release, but the materials do not state that the change is merged, so it is recorded as decided and planned for this release rather than landed. It is also worth holding in mind that this higher default rests on a support report about one legitimate batch client. No broader client usage data is given, so the wider effect of raising the default is not assessed in the record from this session.

The most uncomfortable open item is a test problem whose cause is simply not known yet. One test, test_burst_allowance, fails intermittently, roughly one run in five, and its root cause has not been identified. Nobody should guess at the cause on the basis of what is available so far. Everything else in the suite is green, but that intermittent failure is the main release risk in the current record precisely because its cause is unknown and it fails as often as it does. The next person on this work needs either to identify the root cause and fix it, or to establish with evidence that it is unrelated to the changes described above.

There is one further gap in what is known, around latency. No latency measurement for the token bucket implementation is given in the materials from this session, so compliance with the 5 ms p99 budget is not established for that algorithm. That should be read as unverified, neither passed nor failed, and confirming the token bucket implementation against the budget remains one of the next steps.

So the work that remains, in practical terms, is to merge the token bucket implementation from the prototype branch, to apply the default limit change to 600 requests per minute per client for this release, to get to the bottom of the intermittent test_burst_allowance failure, and to confirm that the token bucket version stays within the latency budget. Until those things are done, the accurate picture is a merged middleware skeleton behind a feature flag and a merged Redis storage fix with a shared key per client, carrying a decided but not yet merged design that uses token bucket at a default of 600 requests per minute per client, with an unresolved intermittent test failure standing in the way of confidence in the release.
