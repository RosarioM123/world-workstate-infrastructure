# Crash-consistency findings, 2026-11-02: the TMPDIR failure

Addendum to `RESULTS.md` (2026-10-15). The original results are not
changed by anything here; see the last section for why.

## Symptom

`tests/test_crash_consistency.py::test_sigkill_mid_transaction_leaves_clean_db`
passes with the default `/tmp` and fails when the test suite runs with
`TMPDIR=/home/hatch/tmp`. The failing assertion is the pytest wrapper's
`assert res["rows"] > 0`: a round ends with zero rows in the database.
Reproduced 4 of 4 runs in this session (2026-11-02), each failing in
about 1 second. It is tempting to file this under "slow disk" and move
on. This document records the actual investigation.

The two filesystems differ: `/tmp` is a 512 MB tmpfs (RAM); the
directory behind `/home/hatch/tmp` is btrfs on a real disk. WORLD
stores each world as a WAL-mode SQLite database (`PRAGMA
journal_mode=WAL` in `src/world/core.py`); WORLD sets no explicit
`PRAGMA synchronous`.

## How the test decides when to kill

`crash_test.run_round` spawned the worker, slept a random delay drawn
from `uniform(0.15, 0.5)` seconds (seeded per round), then sent
SIGKILL. The worker prints `start i` before each update and `done i`
after it commits. The driver's own durability assertions run after the
kill: the world must open, `verify()` must be True, every row's state
must parse as JSON, and `version()` must equal the highest COMMITTED
seq. The pytest wrapper additionally asserts `rows > 0` for each of
its 6 rounds (seeds 20261015 to 20261020) and that at least one kill
landed mid-transaction across the 6 rounds.

So `rows > 0` is not a durability assertion. It is a setup
precondition: it assumes at least one update commits before the kill
arrives. Whether that assumption holds is a race between the drawn
kill delay and everything the worker must do first: interpreter
startup, module import, database creation and schema setup, and a
first 256 KB WAL commit.

## Method and measurements

Worker readiness was measured directly: time from process spawn to
the worker's first `done 0` marker (its first committed update),
5 trials standalone per filesystem, plus 6 trials spawned from inside
a pytest process on the real disk.

| Filesystem | Spawn to `start 0` | Spawn to first commit (`done 0`) |
|---|---|---|
| tmpfs (`/tmp`) | about 0.059 s | 0.061 to 0.063 s |
| btrfs (`/home/hatch/tmp`) | 0.25 to 0.31 s | 0.32 to 0.42 s |

Under pytest on btrfs, spawn to first commit measured 0.32 to 0.38 s,
the same range. The first commit segment alone (`start 0` to
`done 0`, one 256 KB WAL commit) takes about 3 ms on tmpfs and about
70 to 110 ms on the real disk: the difference is fsync and file-growth
cost that tmpfs does not charge.

Controlled rounds replicating `run_round` exactly, with independent
post-kill checks added (`verify()`, `PRAGMA integrity_check`, JSON
parse of every row, version equals max COMMITTED seq):

- btrfs, default delay, 12 rounds (seeds 20261102 to 20261113):
  `rows == 0` in exactly the 6 rounds whose drawn delays were 0.181,
  0.195, 0.213, 0.224, 0.248, and 0.255 s; `rows >= 1` in the 6 rounds
  drawn at 0.306 s and above. Every round passed every durability
  check.
- tmpfs, default delay, same 12 seeds: rows 31 to 113 per round; all
  checks passed.
- btrfs, delayed kill (1.5 to 2.5 s), 4 rounds: rows 17 to 26; all
  checks passed. Giving the worker time to commit removes the failure,
  as the race explanation predicts.
- The pytest test's own seeds on btrfs: rows 3, 0, 0, 2, 1, 2. The two
  zero rounds are seeds 20261016 and 20261017, whose drawn delays are
  0.197 s and 0.248 s, both below the 0.32 s minimum observed
  first-commit latency on this disk. With these seeds the failure on a
  disk of this speed is deterministic, not flaky. Seed 20261015
  (delay 0.47 s) run standalone 5 times gave rows 3 every time.
- One zero round (seed 20261110, delay 0.255 s) had
  `mid_transaction_kill=True`: the kill landed inside the first
  transaction itself. WAL recovery rolled that transaction back,
  leaving an empty database whose chain is valid.

Total: 39 fully checked rounds in this investigation, zero durability
violations.

## Root cause determination

1. **The test is timing-sensitive.** Its kill delay is drawn from
   process spawn, but its `rows > 0` assertion silently requires the
   worker to finish startup plus a first commit inside that delay.
   On tmpfs readiness takes about 0.06 s, comfortably under the
   minimum draw of 0.15 s. On this btrfs disk readiness takes 0.32 to
   0.42 s, squarely inside the 0.15 to 0.5 s kill window, so short
   draws produce an empty database by construction.
2. **There is no durability defect.** In every round, including the
   empty ones, the post-kill database opened cleanly, `verify()`
   returned True, `PRAGMA integrity_check` returned ok, every stored
   state parsed, and `version()` matched the highest committed seq.
   The one mid-first-transaction kill was rolled back by WAL
   recovery, which is the intended semantics. The durability property
   (whatever committed survives intact; nothing torn is visible) held
   in all 39 rounds, in the empty rounds vacuously and in the
   rollback round by correct recovery.
3. **The invalid assumption is about filesystem behavior.** The test
   treated sub-0.15 s worker readiness as a constant. It is a
   property of the storage: WAL commits on tmpfs pay no fsync cost,
   while on a real disk the first commit also pays file creation,
   schema setup, and fsync latency. Nothing in the failure implicates
   SQLite journal semantics; integrity checks passed everywhere.

## Remediation

`crash_test.run_round` now waits for the worker's first `done` marker
(the readiness signal that at least one update has committed) before
starting the random kill delay. No assertion was weakened: the pytest
wrapper still asserts `rows > 0` per round and at least one
mid-transaction kill per run, and the driver still asserts `verify()`,
row parsing, and version consistency after every kill. What changed
is only that the kill now races the worker's transactions, which is
what the test was always meant to measure, instead of racing its
startup, which it was not.

Post-fix validation (2026-11-02): the pytest test passed 20 of 20
runs under `TMPDIR=/home/hatch/tmp` and 20 of 20 under the default
`/tmp`. The harness CLI on btrfs (3 rounds) reported rows 3 to 7 with
3 of 3 kills landing mid-transaction, so the fix does not blunt the
test: kills still land inside transactions, now against a database
that provably has committed work in it.

No code under `src/world` was changed. No change was needed: the
investigation found the defect in the test's setup assumption, not in
WORLD.

## Effect on the 2026-10-15 results

None. The original 15 rounds in `RESULTS.md` ran on tmpfs, where the
first commit lands at about 0.06 s, before every possible kill draw
(the minimum draw is 0.15 s). Those rounds already satisfied the
precondition the fix now enforces explicitly, so the recorded 15 of
15 mid-transaction kills and 0 failures stand as measured.

## Remaining limitations

- Latency figures are from this one machine and its btrfs volume on
  2026-11-02; a slower or busier disk widens the readiness window
  further, which is precisely why the test no longer depends on it.
- The investigation covers process death by SIGKILL, the same scope
  as the original experiment. Power loss and OS crashes remain
  untested, as `RESULTS.md` already states.
